# Generate Change Candidate

ユーザーの指示に基づいて、変更が必要な個所を特定し、それぞれのファイル名・行数とコードの変更内容を提示する。

実現について複数の方法が考えられる場合や、実装量・影響範囲・可読性・エッジケース対応などのトレードオフが存在する場合は、
それぞれの方法の利点・欠点を提示し、いったん一番適切とされる方法での実装を提示する。
- ただし、ユーザーが方法の比較を望む場合は、すべての方法についての実装例を提示する。

1つの変更候補について、
- 修正の場合は最低限の行数にする
- 追加・大編集の場合は、なるべく100行以内、できれば30行程度に収まるように分解する。
  - 関数自体の分割をしてもいいし、処理のまとまりごとに提示する形でもよい
- 1行修正の場合などそこだけ見ても何の修正かわからない場合、周囲のコードを含める。
- 行数を示す場合は、代わりにクリック可能なパスを提示する。

一度に提案する変更箇所は1~5か所程度が一般的だが、
- 内容が定型的だったり、事前確認済みであればより多くの変更箇所を一度に提案してもよい
- 内容が煩雑であったり、影響範囲が広い場合・仕様に影響する場合・確認が必要な場合は、変更を分割して提案することが望ましい

規則的でtrivialな候補よりも、複雑だったり新規性の高い変更を先に提示し、説明する。trivialなもののみの場合はしなくてもよい。

## Coding

特に指示がなければ、既存のコード・既存の変更を調べ、コード構造・実現方法・コメントなどが同じパターン・同じ雰囲気になるように変更を行う。
- それで問題や改善すべき点があれば、それは変更とは別に報告し、勝手に改善バージョンを提示しないようにする。
