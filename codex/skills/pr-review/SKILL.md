# PR REVIEW

（指示がない場合は現在のブランチに関連する）プルリクエストをレビューしてください。

- git管理部分について、（一時的なコード変更は許可しますが）作業完了時には元の状態に戻してください。
- Git Pushなどの消しづらい副作用がある操作は実行しないでください。

## メインプロセス

以下のプロセスを状況に合わせて、サブエージェントで実行してください。それぞれ複数回実行しても問題ありません。
あるプロセスの結果、ほかのプロセスが必要になった場合、それらも実行してください。
それを、あらゆる観点でのチェックが完了するまで繰り返して、指摘・疑問のリストを作成してください。

### A. 背景情報の確認

背景情報・変更内容・既存のコメントの確認をしてください。

- 情報にどのような意図・挙動変更が含まれているか調べて列挙してください。

### B. 変更内容の確認

どのような変更が行われたかを具体的に列挙してください。

### C. 挙動の確認

変更の内容を、コードの呼び出しツリーをたどって確認し、どのような挙動になるかを把握してください。

必要に応じてリンタ・フォーマッタ・テストを実行して、変更の影響を確認してください。

また、その挙動が意図した通りであるかを確認してください。

- どのような変更が行われたかを具体的に列挙してください。
- 変更によって影響を受ける可能性のある箇所を洗い出してください。
- エラー処理や例外処理が適切に行われているかを確認してください。

### D. 意図の確認

変数名やコードフローから、変更によってどのような変化をもたらす意図があるかを確認してください。

また、その意図が背景情報と整合しているかを確認してください。

- どのような意図が含まれる可能性があるかを具体的に列挙してください。
- その意図が背景情報と整合しているかを確認してください。
- その意図がプロジェクト・ソフトウェア全体の意図と明確な関係にあるかを確認してください。

### E. 設計の確認

その変更が「その場所の変更」によって行われるべきかどうかを思案してください。

- その変更が意図を実現するために最適な場所で行われているかを確認してください。
- その変更がそれを実現する責務があるべき場所で行われているかを確認してください。

### F. 命名の確認

変更によって追加・変更された変数名や関数名が適切かを確認してください。

- 変数名や関数名がその役割を正確に表しているかを確認してください。
- 命名が一貫しているかを確認してください。
- 命名がプロジェクト内の他の部分と整合しているかを確認してください。

### G. 変更漏れの確認

今回の変更と同じ設計・意図を持つ箇所に変更漏れがないかを確認してください。
今回の変更に伴って変更が必要な箇所がないかを確認してください。

- 似たようなコードがプロジェクト内の他の場所にないか、そこも変更するべきではないかを確認してください。
- 似たような意図・挙動がプロジェクト内の他の場所にないか、そこも変更するべきではないかを確認してください。
- 関連部分に変更漏れがないかを確認してください。

### H. 自然さ・共通認識の確認

変更が自然であり、チームやプロジェクト内での共通認識と整合しているかを確認してください。

- 変更がチームのコーディングスタイルや慣習に沿っているかを確認してください。

### I. コーディングの確認

変更がコーディング規約やベストプラクティスに沿っているかを確認してください。

- コードが可読性・保守性を考慮して書かれているかを確認してください。
- 不要な複雑さや冗長な記述がないかを確認してください。

### X. レビュー自体の判断

指摘事項になりそうなものがある場合、指摘内容をより的確にすることを考えてください。

そのレビューに基づく改善が、どのように背景情報・挙動・意図・設計と結びついているかを考えてください。

## まとめプロセス

レビューの結果を整理して、ファイルにまとめてください。

- ファイルパス: `/tmp/pr_review_{YYYYMMDD_HHMMSS}_{ANY_TITLE}.txt`
- 疑問リスト: タイトル、ファイルパス、背景情報、変更内容、疑問内容、修正方針
